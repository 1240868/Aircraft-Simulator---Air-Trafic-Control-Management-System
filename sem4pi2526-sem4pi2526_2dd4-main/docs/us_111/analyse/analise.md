# US111 — Analysis

## 1. Overview

Analysis for **US111 — Generate a simulation report**. The FCO triggers the SCOMP C simulation from Java and receives the report file generated by US109.

Related documentation: [requirements/requisitos.md](../requirements/requisitos.md), [sequence-diagrams/readme.md](../Design/sequence-diagrams/readme.md), [class-diagrams/readme.md](../Design/class-diagrams/readme.md).

## 3. Domain concepts

| Concept | Type | Justification |
|---------|------|---------------|
| `SimulationReportResult` | **Application record** | Transports success/failure, content, path — no domain behaviour |
| `SimulationReportService` | **Application service** | Orchestrates ProcessBuilder, file read — infrastructure concern |
| `GenerateSimulationReportController` | **Use case controller** | Authorization + delegation |

> **No EAPLI domain aggregate** is used. The report is an external file produced by SCOMP; Java only orchestrates and presents it. Introducing a `Simulation` aggregate would add complexity without enforcing business invariants in this US.

---

## 4. Separation EAPLI vs SCOMP

| Layer | Module | Component | Responsibility |
|-------|--------|-----------|----------------|
| **Presentation** | EAPLI | `GenerateSimulationReportUI` | Confirmation, display report |
| **Application** | EAPLI | `GenerateSimulationReportController` | Role check |
| **Application** | EAPLI | `SimulationReportService` | Launch C, stream stdout, read file |
| **Application** | EAPLI | `SimulationReportResult` | Result DTO (record) |
| **Simulation** | SCOMP | `flight_sim` / `report.c` | Execute simulation; write `logs/simulation_report.txt` |

## 5. Application-level rules

| # | Check | Where | On failure |
|---|-------|-------|------------|
| 1 | Role `FLIGHT_CONTROL_OPERATOR` | `GenerateSimulationReportController.generateReport()` | `AuthzException` |
| 2 | Directory `scomp.base/` exists | `SimulationReportService` | `SimulationReportResult.failure(...)` |
| 3 | Executable `flight_sim` exists and is executable | `SimulationReportService` | `SimulationReportResult.failure(...)` |
| 4 | Process exit code == 0 | `process.waitFor()` | `SimulationReportResult.failure(...)` |
| 5 | Report file exists after run | `Files.exists(reportPath)` | `SimulationReportResult.failure(...)` |
| 6 | Report content readable | `Files.readString(reportPath)` | `SimulationReportResult.failure(...)` |

## 6. SimulationReportResult

```java
public record SimulationReportResult(
    boolean success,
    String reportContent,   // populated on success
    Path reportPath,        // populated on success
    String errorMessage     // populated on failure
) {
    static SimulationReportResult success(String content, Path path);
    static SimulationReportResult failure(String message);
}
```

Factory methods keep success and failure paths explicit; the UI branches on `success()` without parsing exceptions.

## 7. Process orchestration

```
GenerateSimulationReportUI
        │
        ▼
GenerateSimulationReportController  ── authz ──► FLIGHT_CONTROL_OPERATOR
        │
        ▼
SimulationReportService
        │
        ├── ProcessBuilder("./flight_sim").directory(scomp.base)
        ├── stream stdout → System.out ("[SIM] ...")
        ├── waitFor() → exit code
        └── Files.readString(scomp.base/logs/simulation_report.txt)
```

**Design rationale:** `ProcessBuilder` provides the "seamless experience" requested by the PO — the FCO never leaves the Java application.

---

## 8. Key design decisions

| Decision | Justification |
|----------|---------------|
| No domain aggregate | Report is file-based; no invariants to protect in EAPLI |
| No RDBMS persistence | PO clarification: file system storage is the requirement |
| `SimulationReportResult` as record | Lightweight transport; tested without mocking file I/O in controller tests |
| Real-time stdout streaming | Operator visibility during long-running C simulation |
| Injectable `SimulationReportService` | Controller tests use stub service; no subprocess in unit tests |
| Default path `scomp.base/` | Matches monorepo layout; configurable via constructor |

---

## 9. Report content (produced by US109 / SCOMP)

The C module writes a structured text report including:

1. Simulation summary (totals, violations, PASS/FAIL)
2. Execution status per flight
3. Safety violation events (timestamp, 3D positions, ENU velocity, separation)
4. Final verdict

US111 **does not transform** this content — it reads and displays it as-is.
